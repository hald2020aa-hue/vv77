# المرحلة 3A — توافق SQL وتشخيص الفهارس

المرجع: فرع `feature/storage-phase2`، الالتزام `83e2fc13b65f188f39b5ae9a402579ab59c681b0`، بناء Actions رقم 45847491989 (نجاح).

## التنفيذ
- استعلام `libraryQuery` في `RawQueries.kt` كان يستخدم علامات اقتباس مزدوجة حول قيمتي `N/A` و` [.] ` في تجميع المترجمين مرتين. استبدلت بعلامات اقتباس SQL المفردة دون تغيير الاستعلام أو الفلاتر أو أسماء أعمدته.
- أضيف فحص SQLite إلى سلسلة CI الحالية قبل Gradle، مع الإبقاء على جميع الاختبارات السابقة.
- لا تغيير في schema أو إصدار قاعدة البيانات (21)، أو معرّف التطبيق، أو المصادر، أو ملفات التنزيل أو القارئ أو الاسم الظاهر «فيروس مانجا».

## الاختبار
`python3 qa/core/check_library_sql.py` يستخرج الاستعلام من Kotlin ويحل الثوابت من ملفات الجداول، ثم يشغله على قاعدة SQLite اصطناعية. تحقق من تطابق الصفوف قبل وبعد، نجاح الوضع الصارم DQS_DML=OFF (عندما تتوفر API)، الفئات المتعددة والعدادات والقيم الفارغة والمفضلة والتتبع.

النتيجة المحلية: PASS للثلاثة فحوص؛ SQLite 3.46.1. في EXPLAIN QUERY PLAN ظهرت فهارس تلقائية على النتائج المجمعة CC وC وRC وR وB وS. هذه ليست دليلًا على فقدان فهرس دائم على الجدول الأصلي. `mangas._id` معرف PRIMARY KEY و`chapters.manga_id` مفهرس بالفعل. لا توجد هنا بيانات الهاتف أو خطة استعلام Android الفعلية؛ لا يمكن تأكيد حل كل تحذيرات automatic index أو قياس تحسن السرعة. لا تضف فهرسًا على المفتاح الأساسي دون دليل. أي فهرس جديد يحتاج خطة هجرة مستقلة وموافقة واختبار الترقية.

## غير مختبر
Android/Gradle بعد هذه الرقعة، الأداء على جهاز فعلي، الترقية/الحذف على بيانات المستخدم الحقيقية، والتصميم المرئي. تحسينات الصور والقوائم والقارئ والنسخ الخمس ليست ضمن هذه الرقعة.
